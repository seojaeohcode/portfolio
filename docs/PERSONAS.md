# 신입 AI·소프트웨어 엔지니어 포트폴리오 검수 페르소나

조사일: 2026-11-15. 대상: 지방 국립대 인공지능학부 신입 지원자, 해커톤·공모전 수상과 실서비스형 프로젝트 경험 보유.
공개 글을 바탕으로 만든 합성 페르소나다. 특정 회사의 공식 채용 기준이나 실제 인터뷰 참여자를 뜻하지 않는다.
하루 검토 건수·열람 환경·10초/60초/5분 구간은 **사이트 검수용 가정**이다. ‘실제로 하는 말’은 출처의 관심사를 구어체로 재구성한 대사이며 직접 인용이 아니다.
경력직 자료에서는 평가 관점만 가져왔다. 신입에게 매출·대규모 트래픽·논문 실적을 일괄 요구하지 않으며, 학교 소재지에 따른 선호는 추정하지 않는다.
아래 ‘합격’은 **다음 검토로 넘길 만큼 정보를 전달하는 사이트의 기준**이다. 채용 합격을 보장하지 않는다.
검수는 프로젝트 3개 이상을 넣고 진행한다. 현재 양식의 `content/` 예시값은 가상임을 구별하고, 실제 성과·측정값으로 판정하지 않는다.

## 1. 대기업 인사팀 채용담당 — 현업에 넘길 근거를 찾는다

- 상황: 공채 마감 주간, 하루 지원서 100~200건을 회사 PC의 채용 시스템에서 훑고 관심 지원자의 웹 링크를 연다(가정; 전부 웹사이트를 열지는 않음).
- 근거: 업무·기여·성과를 보는 [야나두 채용팀 인터뷰](https://hr.rememberapp.co.kr/blog/customer-stories/yanadoo), 역할과 기간의 개연성을 확인하는 [리멤버 검토 가이드](https://hr.rememberapp.co.kr/blog/insights/ai-hiring-resume-screening-checklist). 야나두의 하루 100건은 경력 인재 소싱 사례로, 대기업 신입 공채 통계가 아니다.
- 10초: 이름·전공·졸업 시점, 지원 직무와 이어지는 대표 프로젝트, 본인이 만든 결과 하나.
- 60초: 프로젝트별 기간·역할·완성 수준, 수상명·주최·연도, 같은 프로젝트의 복수 수상 여부.
- 5분: 이력서와 사이트의 내용 일치, 성과를 확인할 근거, 현업에게 전달할 추천 이유.
- 바로 닫는 신호: 수상 배지만 가득함; 팀 성과와 개인 역할이 섞임; 핵심이 PDF 안에만 있음; 기간·수치가 서로 다름.
- 붙잡는 신호: 전공 경험이 채용 직무와 연결됨; 프로젝트 하나를 ‘문제→담당한 일→결과’로 설명할 수 있음; 증빙 위치가 분명함.
- 실제로 하는 말(재구성): “우리 모집 직무랑 이어지는 경험이 어디죠?” / “이 상들은 같은 프로젝트에서 받은 건가요?” / “현업에 넘길 때 이분이 한 일을 한 문장으로 설명할 수 있겠어요.”

합격 기준:

- [ ] 첫 화면을 10초 본 뒤 이름·지원 분야·대표 프로젝트의 해결 문제를 말할 수 있다.
- [ ] 프로젝트 3개 각각에 기간·팀 규모·본인 담당 범위가 있고, 수상은 해당 프로젝트 아래에 주최·연도와 함께 묶인다.
- [ ] 60초 안에 대표 결과와 증빙 링크를 찾고, PDF를 내려받지 않아도 핵심 내용을 이해할 수 있다.

## 2. 스타트업 개발 리드/CTO — 작은 기능을 맡겨 끝까지 낼 수 있는가

- 상황: 출시 업무 사이 하루 후보자 5~10건을 노트북에서 확인하고, 채용 담당자가 보낸 프로젝트 링크부터 연다(가정).
- 근거: 역할 범위·완성 경험·불확실성 속 판단을 강조한 [모두의 CTO 글](https://cofounders.tistory.com/116), 자율적 문제 정의와 사용자 문제 해결을 설명한 [업스테이지 구성원 인터뷰](https://www.upstage.ai/careers/careertalk-sep25). 첫 개발자 채용 조언을 신입의 소규모 과제 수행 관점으로 낮춰 적용한다.
- 10초: 누구의 불편을 해결하는 서비스인지, 지금 무엇이 작동하는지.
- 60초: 팀에서 직접 맡은 경계, 배포 여부, 데모와 실제 사용자 이용의 구분.
- 5분: 제한된 시간·비용에서 고른 구현, 배포 후 문제와 수정, 동료에게 넘길 수 있는 설명.
- 바로 닫는 신호: 모든 프로젝트가 대회 종료에서 멈춤; 끊긴 데모에 설명 없음; ‘풀스택 전담’만 있고 구현 범위가 없음.
- 붙잡는 신호: 작은 기능이라도 작동함; 피드백으로 바꾼 흔적; 못 한 범위와 다음 판단이 솔직함.
- 실제로 하는 말(재구성): “이 기능은 혼자 어디까지 맡았어요?” / “대회 끝나고 써본 사람 반응으로 바꾼 게 있나요?” / “일정이 짧았을 때 뭘 빼기로 했어요?”

합격 기준:

- [ ] 대표 프로젝트의 데모 영상이 본문에 보이고, 로그인 없이 핵심 사용 흐름을 확인할 수 있다.
- [ ] 한 프로젝트 이상에 배포·운영·종료 상태와 후속 개선 사례가 있다. 운영하지 않았다면 그 사실과 검증 범위를 적는다.
- [ ] 본인이 결정한 구현 하나에 제약·선택·포기한 대안·결과가 연결되어 있다.

## 3. AI 연구 리드 — 개선이라는 주장을 검증할 수 있는가

- 상황: 실험 리뷰 사이 하루 후보자 3~5건을 연구용 PC에서 읽으며, 포트폴리오의 결과표와 실험 자료를 함께 연다(가정).
- 근거: 데이터·평가 기준 설계, 실패 분석, 가설 검증을 요구하는 [업스테이지 LLM Eval 공고](https://kr.linkedin.com/jobs/view/독파모-ai-research-engineer-llm-eval-at-upstage-4281479595). 공고의 연구 업무를 학부 프로젝트 규모의 검증 기준으로 해석했다.
- 10초: 해결할 과제, 본인이 바꾼 부분, 단순 API 활용인지 모델·데이터·평가 연구인지.
- 60초: 비교 기준, 데이터 출처·규모, 평가 지표, 개선을 보여주는 표나 그래프.
- 5분: 데이터 분리와 누수 가능성, 비교 조건, 실패 사례, 실험을 다시 확인할 방법.
- 바로 닫는 신호: ‘정확도 향상’만 있고 분모·비교 대상이 없음; 성공 예시만 제시; RAG·XAI 같은 이름을 성능 증거로 사용.
- 붙잡는 신호: 작은 실험도 조건이 명확함; 성능이 떨어진 사례를 설명함; 기존 방법과 자기 기여의 경계가 보임.
- 실제로 하는 말(재구성): “비교 대상도 같은 데이터로 평가했나요?” / “안 되는 사례를 보고 다음 실험은 어떻게 정했어요?” / “이 결과에서 본인이 바꾼 부분은 어디인가요?”

합격 기준:

- [ ] AI 대표 프로젝트 하나에 과제·가설·비교 기준·평가 지표와 결과표가 있고, 미측정 항목은 미측정으로 표시한다.
- [ ] 데이터 출처·규모·학습/평가 분리 방식과 비교 조건을 찾을 수 있고, 실험 설정 또는 재현 문서로 연결된다.
- [ ] 실패 사례와 한계를 각각 하나 이상 제시하며, 모델·데이터·검색·프롬프트 중 자신의 변경 지점을 도식에 표시한다.

## 4. DX·AX 현업 리더 — 우리 업무에 넣으면 무엇이 달라지는가

- 상황: 현업 회의 전후 하루 추천 후보자 2~4건을 사무실 PC에서 검토하며, 기술 용어보다 사용자 화면을 먼저 본다(가정).
- 근거: 기존 업무 분석, 데이터 준비도, 사용자 피드백과 예외 대응을 다룬 [LG CNS AX Master Plan](https://connect.lgcns.com/language-masters/ko/moa/insight/detail.agenticai-ax-master-plan-2603-4). 채용 인터뷰가 아닌 현업 적용 자료에서 평가 관점을 도출했다.
- 10초: 어느 사용자의 어떤 업무가 달라지는지.
- 60초: 도입 전후 작업 흐름, 자동 처리와 사람 확인의 경계, 실제 적용인지 시제품인지.
- 5분: 입력 데이터 확보, 기존 시스템 연결, 오답·장애 때 처리, 효과와 운영 부담의 측정 근거.
- 바로 닫는 신호: 챗봇 화면만 있고 업무 맥락 없음; 근거 없이 ‘업무 혁신’; 정확도만 내세우고 오답 뒤 처리가 없음.
- 붙잡는 신호: 현업 언어로 설명한 전후 흐름; 사람이 다시 확인하는 지점; 기대 효과와 측정한 효과의 구분.
- 실제로 하는 말(재구성): “그래서 담당자가 하던 일 중 어디가 줄어드나요?” / “잘못 답하면 누가 확인하죠?” / “이건 현장에서 재본 결과인가요, 예상인가요?”

합격 기준:

- [ ] 프로젝트 하나 이상에 사용자·업무 문제와 도입 전후 흐름도가 있고, AI가 담당하는 단계를 표시한다.
- [ ] 시간·오류·비용 중 주장한 효과에 측정 방법·조건을 붙인다. 미실증이면 기대 효과로 명시하고 검증 계획을 적는다.
- [ ] 데이터 입력부터 결과 확인까지 시연으로 따라갈 수 있고, 오답·예외 시 사람에게 넘기는 방식과 적용 한계가 보인다.

## 5. 테크 기업 시니어 엔지니어(면접관) — 설명과 구현이 맞는가

- 상황: 면접 준비일에 하루 배정 후보자 2~3건을 개발 노트북에서 정독하며, 사이트 옆에 저장소와 질문 메모를 띄운다(가정).
- 근거: 문제·원인·대안·평가를 연결한 [우아한형제들 개발자의 이력서 회고](https://techblog.woowahan.com/2531/), 구현·트러블슈팅·실행 방법을 강조한 [잡코리아 가이드](https://www.jobkorea.co.kr/recruit/careers/articles/developer-resume-guide). 전자는 개인 경험이며 현행 회사 심사표가 아니다.
- 10초: 깊게 물을 대표 구현과 지원 분야의 연결.
- 60초: 구조도, 기술 선택 이유, 실제 담당 코드로 가는 링크.
- 5분: 코드·테스트·PR에서 설명을 대조하고, 실패 조건과 대안의 장단점을 질문으로 만든다.
- 바로 닫는 신호: 기술 로고만 많음; 저장소 첫 화면에서 근거를 못 찾음; 성능 수치의 조건이 없음; 팀 코드를 전부 자기 작업처럼 설명.
- 붙잡는 신호: 구체적인 코드 위치; 재현 가능한 문제 해결 기록; 리뷰를 받고 바꾼 이유; 모르는 범위를 인정하는 설명.
- 실제로 하는 말(재구성): “이 구조를 고른 이유를 코드에서 같이 볼까요?” / “다른 방법도 검토했나요?” / “그 버그가 다시 안 생기는 건 어떻게 확인했어요?”

합격 기준:

- [ ] 대표 구현 설명에서 관련 파일·PR·커밋 또는 공개 가능한 코드 발췌까지 두 번 이내 클릭으로 도달한다.
- [ ] 기술적 결정 하나에 대안·선택 이유·불리한 점을 적고, 구조도와 구현 설명이 일치한다.
- [ ] 문제 해결 사례 하나에 재현 조건·수정 내용·검증 방법이 있으며, 본인 작성 부분과 팀 작업을 구별한다.

## 공통 결론

- 첫 화면에서 대표 문제와 결과를 이해하게 한다. 시간 구간은 검수 장치이며 채용업계의 보편 통계가 아니다.
- 프로젝트를 중심으로 묶고 시간 흐름을 보여준다. 한 프로젝트의 복수 수상은 그 아래에 연결하며, 상의 개수를 역량 점수로 치환하지 않는다.
- 본인 역할·선택 이유·검증 근거를 붙인다. 학교 소재지를 임의로 감점하거나, 수상만으로 구현 역량을 확정하지 않는다.
- 요약은 펼치지 않아도 읽히고, 더 볼 곳은 ‘실패 사례·설계 선택·실험 결과’처럼 내용이 예상되는 제목으로 표시한다.
- 시연은 본문에서, 발표자료는 웹에서 확인한다. 구조도·전후 화면·비교표로 글을 보완하고 PDF 없이도 판단할 수 있게 한다.
- 실서비스형·실제 운영·실험·예상을 구분한다. 수치가 없으면 관찰한 변화와 한계를 쓰고, 양식의 가짜 값으로 성과를 주장하지 않는다.
- 프로젝트 3개 이상으로 다섯 관점의 15개 항목을 점검한다. 같은 내용을 반복하기보다 요약→사례→근거로 이어지고, 채용 지원은 각 공고의 지정 형식을 따른다.
