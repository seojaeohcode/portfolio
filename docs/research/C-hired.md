# C. 실제 합격자와 공개 개발자 이력서·포트폴리오 사례

조사일: 2026-11-15. 라이브 검색 후 본문을 직접 연 공개 원문 12개와 합격 후기 4개를 비교했다. **12개 모두가 신입 합격 제출본이라는 뜻은 아니다.** 신입·주니어 합격 확인, 재직 확인, 경력자 참고 사례를 아래에서 구분한다.

## 확인 범위와 읽는 법

- **합격 확인**은 작성자의 최종 합격·입사 진술을 뜻한다. 회사의 독립적인 인증이나 포트폴리오가 합격 원인이었다는 검증은 아니다. 인턴 합격을 정규직 전환으로 해석하지 않았다.
- **재직 확인**은 공개 이력서에 회사·직무·기간이 적혀 있다는 뜻이다. 당시 연차, 채용 전형, 실제 제출본은 별도 근거가 없으면 미확인이다. 현재 페이지의 ‘재직 중’도 원문 표기이며 현시점 재직을 보증하지 않는다.
- 첫 화면은 **문서 상단의 콘텐츠 구성**을 분석했다. 웹 본문·이미지 설명·임베드 표시는 읽었지만 브라우저 연결 실패로 실제 화면의 접힘 위치, 색상, 반응형, 모션은 검증하지 못했다. 이미지가 있다는 것과 이미지 내용을 직접 판독한 것은 구분했다.
- 분량은 웹 문서 수·섹션·프로젝트 수로 기록했다. 웹페이지를 임의의 PDF 장수로 환산하지 않았다. 성과는 원문의 자기보고이며 실험·서비스 지표를 재검증하지 않았다. 직접 인용 없이 요약했고 판단·설계 제안에는 [추정]을 붙였다.
- 추천 경로: [코딩몬스터 공개 이력서 모음](https://github.com/codingmonster-tv/Awesome_Resume_Portfolio), [Wonny의 공개 이력서 추천 목록](https://wonny.space/writing/work/engineer-resume), [FE Korea 국내 포트폴리오 모음](https://fekorea.webflow.io/). 목록 등재는 합격 증거가 아니며 추천 빈도 순위도 아니다.

### 01. 이도현 — 토스 iOS 신입 합격 확인

- 출처: [웹 포트폴리오](https://leedh2004.github.io/), [2021 토스 NEXT 합격 후기](https://walwal234.tistory.com/104), [후기 블로그의 포트폴리오 연결](https://walwal234.tistory.com/107). 본인이 경력 0년차 지원·최종 합격을 명시한다. 공개 웹은 입사 이후 정보도 포함하므로 제출 당시 버전과 동일하다고 단정할 수 없다.
- 첫 화면·순서: 이름·간단한 인사·프로필 이미지·섹션 메뉴 → 경험 → 학력 → 기술 → 수상·자격. 경험 안에 회사·인턴·외주·공모전 프로젝트가 함께 들어간다.
- 프로젝트 구조: **STRIDE**는 기간 → SW마에스트로 참여 맥락 → 모바일 앱 담당 → Flutter 앱 배포·분석 도구·React 도구 구현 → 주요 프로젝트 선정 순이다.
- 문제·기술선택·해결·성과: 분석과 크래시·리텐션 확인을 통한 업데이트는 적혀 있다. 최초 사용자 문제, Flutter 선택의 대안 비교, 개별 장애 해결 과정·정량 효과는 이 항목에서 확인되지 않는다.
- 분량: 단일 장문 웹. 경험 아래 여러 프로젝트를 연속 배치하며 프로젝트당 설명과 기능 불릿, 일부 영상이 붙는다.
- 시각·링크: 확대 이미지 안내와 앱 작동·발표 영상 임베드 표시. GitHub·스토어·문서·보도·결과 링크 라벨을 프로젝트 가까이에 배치한다. 영상 재생과 모든 링크 목적지는 미검증이다.
- 차별점 [추정]: 모바일 결과물을 실행 영상으로 바로 확인하게 하는 구성이 강점이다. 경험 종류가 섞여 있어 프로젝트별 대표 결과를 따로 강조하면 더 빠르게 읽힐 수 있다.

- 문제·기술선택·해결·성과: 제작 이유와 JSON·CLI 선택 근거는 명확하다. 구체적인 오류 해결 기록과 절감 시간은 없다. 공개 저장소에 사내 추가 기능이 빠져 있다는 한계를 명시한다.

- 시각·링크: 본문에 전체 구조와 YouTube 시연 안내가 있으나 파싱 결과만으로 이미지·플레이어의 정상 표시를 확인하지 못했다. 프로젝트 목차 앵커와 서버·앱별 저장소 링크가 있다.
- 차별점 [추정]: 문제 발생 맥락과 공개 코드의 한계를 함께 적어 실무 경험과 공개 증거의 경계를 분명히 한다. 화려한 웹사이트 없이도 기술 선택을 설명할 수 있는 사례다.

### 03. 정종윤·재그지그 — 네이버 신입 공채 합격, 현재는 경력 누적본

- 분량: 단일 장문 웹, 회사 4개와 그 안의 여러 서비스, 개인 프로젝트 2개를 포함한다. 각 프로젝트는 소개와 짧은 기여 불릿으로 요약된다.
- 시각·링크: 회사·개인 프로젝트 로고 이미지, 기술 태그, 서비스 링크와 구현 설명에 직접 걸린 기술 글 링크가 있다. 본문 시연 영상은 확인되지 않았다.
- 차별점 [추정]: 회사 → 프로젝트 → 기여 → 설명 글로 내려가는 계층이 명료하다. 기술적 변경이 사용자 기능·사업 범위에 미친 영향을 같은 항목에서 읽을 수 있다.

**해석 한계:** 공개를 선택한 사람만 남는 표본이고, 합격 이후 경력이 누적된 문서가 많다. 경력자 참고 사례의 완성도·성과 규모를 신입의 합격 기준으로 읽으면 안 된다. 특히 AI 기업 신입의 실제 제출본과 LINE 신입의 전체 포트폴리오는 이번 조사에서 확보하지 못했다. 합격 확률·회사별 선호·색상 효과는 이 표본으로 판단할 수 없다.

## 포트폴리오 웹사이트 설계에 바로 쓰는 시사점

아래는 사례 비교에서 도출한 [추정] 설계 기준이며, 채용 효과가 검증된 규칙은 아니다.

- [ ] 첫 화면에서 이름·지원 분야·대표 프로젝트의 문제와 결과를 추가 클릭 없이 읽을 수 있다.
- [ ] 프로젝트 3개 이상을 넣어도 각각의 이름·기간·담당 범위·대표 결과를 같은 위치에서 찾을 수 있다.
- [ ] 프로젝트마다 사용자 문제, 본인 역할, 기술 선택 이유, 해결 과정, 결과를 구분하며 근거가 없는 항목은 만들어 채우지 않는다.
- [ ] 핵심 기술마다 그 기술이 바꾼 실제 기능·성능·운영 방식을 적고, 숙련도 퍼센트 막대는 사용하지 않는다.
- [ ] 대표 프로젝트마다 실제 화면·구조도·실험 그림 중 이해에 필요한 자료를 하나 이상 붙이고 설명 문장과 연결한다.
- [ ] 시연 영상은 프로젝트 안에서 볼 수 있고, 발표자료는 웹에서 열람할 수 있으며 PDF를 열지 않아도 핵심을 이해할 수 있다.
- [ ] 상세를 접더라도 문제·담당 범위·핵심 결정·결과는 남아 있고, 펼치기 제목이 안쪽의 구체적인 내용을 알려준다.
- [ ] 성과 수치에는 기준값·측정 조건·기간을 붙이고, 팀 성과와 개인 기여 및 기대 효과와 달성 결과를 구분한다.
- [ ] 프로젝트의 주장 가까이에 해당 저장소·PR·실험·기술 글을 연결하고, 공개 상태와 링크 동작을 제출 전에 점검한다.
- [ ] 프로젝트 3개가 들어간 화면을 인사·개발 리드·연구 리드 관점에서 검토해 대표 결과, 설계 근거, 평가 조건을 각각 찾을 수 있는지 확인한다.
