# 한국 IT 서비스 UI: 정보를 한눈에 전달하는 방식

조사일: 2026-11-15. 목적: 서재오 포트폴리오 **양식**에 차용할 정보 구조와 표현 규칙.

## 근거와 관찰 범위

- 라이브 웹 검색 후 본문을 실제 열람한 공식 페이지만 인용했다. 검색 결과의 요약문만으로 분석하지 않았다.
- **이미지 관찰**은 공식 글에 실린 화면 예시를 직접 열어 확인했다는 뜻이다. 로그인한 앱의 현재 화면을 조작한 것은 아니다.
- **본문 관찰**은 HTML의 제목·문장·항목 순서 확인이다. 실제 첫 화면의 접힘선, 카드 외형, 여백과 글자 크기는 확인하지 못했다.
- 브라우저 연결 및 Chrome 화면 확보에 실패했다. 따라서 본문만 확보한 페이지의 시각적 해석은 **[추정]**, 미확인 사항은 그대로 표시했다.
- 원티드 이력서 소개는 웹 도구에서 차단됐으나 직접 HTTP 열람으로 정상 본문을 확인했다. 공식 이미지도 HTTP로 열람했으며 파일로 저장하지 않았다.
- 다크 화면을 못 봤다는 사실은 다크 모드 미지원이라는 뜻이 아니다. 과거 화면 예시는 연도를 명시했다.
- 아래 픽셀값은 서비스의 실측값이 아니라 **포트폴리오 적용 제안**이다. 예시 화면의 실적·숫자를 개인 실적으로 가져오지 않는다.

## 대상별 분석

### 1. 토스 앱 — 요약 금액 → 구성비 → 상세 목록

근거: [2020년 다크 모드 소개](https://toss.im/tossfeed/article/toss-darkmode), [공식 소비분석 비교 이미지](https://static.toss-internal.com/ipd-tcs/toss_core/staging/ac29df49-e686-42fb-bbcc-355b648fc280). **이미지 관찰, 현행 앱 검증 아님.**
- 첫 화면 위계: 예시 화면의 월 선택·탭 아래 총지출, 도넛과 범례, 항목별 목록 순서. 숫자의 전체 의미를 먼저 잡고 세부로 내려간다.
- 숫자·성과: 합계는 굵고 크게, 개별 항목은 비율과 금액을 함께 표시한다. 경력 표현은 해당 없음. 전체와 부분의 관계를 보여주는 사례다.
- 카드·리스트: 차트 영역과 목록 영역을 넓은 가로 구획으로 나눈다. 목록은 아이콘·항목명·수치·진입 화살표를 같은 위치에 반복한다.
- 여백·글자·문체: 항목 사이 세로 간격이 넓고 합계가 범례보다 크다. 화면은 짧은 명사형, 설명 글은 해요체다. CSS 크기는 미측정.
- 다크: 밝고 어두운 화면에서 배치와 차트 범주는 유지한다. 배경·글자·구분 영역의 명도를 바꾼다. 색만으로 항목을 식별하지 않도록 범례도 남긴다.

### 2. 토스 채용 — 검색할 조건을 먼저 제공

근거: [토스 채용](https://toss.im/career) → [공고 페이지](https://toss.im/career/jobs). **본문 관찰.**
- 첫 화면 위계: 문서 앞부분은 채용 메시지, 검색 입력, 직군·계열사·고용형태 선택, 공고 수, 관련 글 순서다. 실제 접힘선은 미확인.
- 숫자·성과: 열람 응답에는 공고 수가 0으로 표시됐다. 동적 데이터 미수신 가능성이 있어 실제 채용 규모로 해석하지 않는다. 개인 성취 표현은 미관찰.
- 카드·리스트: 조건 선택과 콘텐츠 탐색을 구분한다. 공고 카드 외형·행 간격·글자 크기는 미확인. [추정] 분류를 먼저 좁히게 하는 탐색 구조다.
- 문체·다크: 이번 응답은 영문 메시지와 짧은 필터명 중심이다. 한국어 해요체 사용 및 다크 모드 동작은 확인하지 못했다.

### 3. 토스피드 — 제목에 상황, 부제에 맥락

근거: [토스피드](https://toss.im/tossfeed). **본문 관찰.**
- 첫 화면 위계: 카테고리 내비게이션 뒤 추천 콘텐츠의 제목·부제·소개가 나온다. 실제 화면 안에서 보이는 분량은 미확인.
- 숫자·성과: 열람 당시 대표 글은 현장의 문제와 실행을 설명하고, 이용 건수·비율·기준 시점으로 결과를 뒷받침한다. 숫자 크기나 강조색은 미확인.
- 카드·리스트: 대표 콘텐츠와 주제별 이동 경로가 존재한다. 격자·카드 수와 여백은 확인하지 못했다. [추정] 제목과 부제로 읽을 이유를 먼저 제공한다.
- 글자·문체·다크: 제목·부제·소제목의 문서 위계를 확인했다. 대표 글은 서술형 문장, 안내에는 해요체가 섞인다. 렌더링된 글자 크기와 다크 모드는 미확인.

### 4. 토스 디자인 원칙·Simplicity — 읽기 전에 이해시키기

근거: [제품 원칙](https://toss.im/tossfeed/article/tossproductprinciples), [Simplicity 사례 글](https://toss.tech/article/mydoc). **본문 관찰.**
- 첫 화면 위계: 제품 원칙 글은 제목·날짜·읽는 시간과 번호가 붙은 원칙 목록을 제공한다. 설명을 찾을 단위가 명확하다. 실제 첫 화면 배치는 미확인.
- 숫자·성과: 원칙 번호는 순서 표지다. 성과 숫자로 해석하지 않는다. 사례 글은 복잡한 제품을 다시 설계한 판단을 설명한다.
- 카드·리스트: 원칙별 소제목과 설명을 반복한다. [추정] 한 화면의 핵심 메시지를 하나로 줄이라는 원칙은 프로젝트 요약에도 적용할 수 있다.
- 여백·글자·문체·다크: 정확한 크기·간격·다크는 미확인. 제품 원칙은 영문, 사례 글은 해요체 중심. 친숙한 개념, 행동 전 가치 설명, 명확한 다음 행동을 강조한다.

### 5. 당근 채용 — 실제 문제로 직무를 설명

근거: [당근 채용](https://careers.daangn.com/). **본문 관찰.**
- 첫 화면 위계: 모집 안내 뒤 큰 주제의 제목, 사업 영역과 설명, 직무 검색이 이어진다. 이후 일하는 방식·직군별 공고·현장의 질문으로 확장한다. 실제 첫 화면 범위는 미확인.
- 숫자·성과: 직군명에 공고 수를 붙인다. 거리·시간·거래 금액 같은 숫자는 사용자의 상황을 구체화한다. 개인 경력 대신 팀이 해결할 문제를 보여준다.
- 카드·리스트: 문제 질문마다 서비스 영역과 구성원 이름을 붙인다. [추정] 프로젝트도 기술명보다 해결 대상이 드러나는 질문으로 탐색시키기 좋다.
- 여백·글자·문체·다크: 제목 위계만 확인했으며 크기·간격·색상은 미확인. 현재 메인 설명은 합니다체, 모집 안내에는 해요체가 섞인다. 브랜드 전체를 해요체로 단정하면 안 된다.

### 6. 당근 디자인 글 — 정보마다 역할을 정해 위계 유지

근거: [SEED 개편 글](https://seed-design.io/updates/how-seed-evolved), [공식 프로필 예시](https://seed-design.io/updates/how-seed-evolved/how-seed-evolved-10.webp). **본문·이미지 관찰.**
- 첫 화면 위계: 프로필 예시는 사진·이름, 수정 기능, 대표 신뢰 지표, 보조 지표, 활동 정보 순서다. 글의 첫 화면은 미확인.
- 숫자·성과: 대표 지표는 색과 굵기로, 보조 지표는 설명과 묶어 표시한다. 글은 개편 내용 다음에 행동 변화 결과를 제시한다. 서비스 측 보고이며 개인 성과가 아니다.
- 카드·리스트: 대표 지표 아래 보조 지표를 나란히 두고, 활동 기록은 별도 배경 영역에 묶는다. 같은 의미끼리 가까이 놓인다.
- 여백·글자·문체: 이름·구획 제목·설명의 크기와 명도가 다르다. 글은 스타일 종류를 줄이고 역할을 명확히 했다고 설명한다. 해요체 중심, 픽셀값은 미측정.
- 다크: 본문에서 배경을 더 어둡게, 앞 레이어를 상대적으로 밝게 조정했다고 명시한다. 이미지 대체텍스트와 실제 이미지 내용이 어긋나는 항목이 있어 다크 설명은 본문에만 근거한다.

### 7. 리멤버 프로필·커리어 — 현재 맥락과 상세 이력 분리

근거: [프로필 작성 도움말](https://support.rememberapp.co.kr/hc/ko/articles/360000347961-%ED%94%84%EB%A1%9C%ED%95%84-%EC%9E%91%EC%84%B1%ED%95%98%EA%B8%B0), [채용 담당자용 조회 도움말](https://hr-support.rememberapp.co.kr/hc/ko-kr/articles/40958266228505). **본문·첨부 이미지 관찰.**
- 첫 화면 위계: 상세 예시에서 상태·갱신 정보, 이름·현재 회사·직무, 자기소개 순으로 나타난다. 우측에는 메모와 검토 이력이 분리돼 있다.
- 숫자·성과: 날짜는 보조 명도, 이름과 현 직장은 굵게 표시한다. 총 경력·수상·논문·문서 링크가 별도 입력 항목이다. 작성 완성도는 성취가 아닌 입력 상태다.
- 카드·리스트: 작성 안내는 항목별 입력 카드, 열람 화면은 큰 프로필 영역과 보조 패널을 사용한다. 관리용 카드 구조와 독자용 이력 구조를 구별해야 한다.
- 여백·글자·문체: 이름이 가장 크고 현재 회사·구획명이 그다음이다. 긴 소개와 구획 사이에 여백을 둔다. 화면은 명사형, 도움말은 설명형 존댓말이다.
- 다크: 확인한 예시는 밝은 배경이다. 다크 지원 여부는 미확인. 포트폴리오에는 현재 프로젝트의 기간·역할만 옮기고 구직 상태·조회 수·제안 버튼은 차용하지 않는다.

### 8. 원티드 프로필·이력서 — 회사 아래 프로젝트, 프로젝트 옆 근거

근거: [이력서 소개·공개 샘플](https://www.wanted.co.kr/cv/intro), [프로필 도움말](https://help.wanted.co.kr/hc/ko/articles/20541578134041-%ED%94%84%EB%A1%9C%ED%95%84%EC%9D%98-%EA%B2%BD%EB%A0%A5%EB%85%84%EC%88%98%EB%A5%BC-%EB%B3%80%EA%B2%BD%ED%95%98%EA%B3%A0-%EC%8B%B6%EC%96%B4%EC%9A%94), [검토 화면 설명](https://help.wanted.co.kr/hc/ko/articles/51607472609817--%EA%B8%B0%EC%97%85-%EC%B1%84%EC%9A%A9-%EC%97%90%EC%9D%B4%EC%A0%84%ED%8A%B8-%EA%B8%B0%EB%8A%A5-%EC%B6%94%EA%B0%80). **샘플 본문·도움말 이미지 관찰.**
- 첫 화면 위계: 프로필 예시는 사진·이름, 직무 정보, 활동 수치, 설정 순서다. 공개 이력서 샘플은 소개·역량·경력·학력·스킬·수상·링크 순서다. 샘플의 접힘선은 미확인.
- 숫자·성과: 샘플은 총 경력과 회사별 기간을 따로 적고 프로젝트 설명에 개선 수치를 붙인다. 수치는 제공자가 만든 샘플이며 개인 포트폴리오에 복사할 근거가 아니다.
- 카드·리스트: 회사 아래 프로젝트별 기간·수행 내용·성과·기술이 묶인다. 검토 화면은 후보자 목록과 이력서를 함께 볼 수 있게 한다.
- 여백·글자·문체: 프로필 이미지에서는 이름이 가장 크고 활동 수치는 작다. 검토 예시는 같은 레이블과 구획을 반복한다. 샘플은 개조식, 소개 페이지는 해요체·권유형이 섞인다.
- 다크: 도움말 화면 예시는 밝다. 이력서 샘플의 실제 글자 크기·여백과 다크 모드 동작은 미확인. [추정] 프로젝트 안에 기술과 결과를 붙이면 독자가 연결 관계를 덜 추론하게 된다.

### 9. 프로그래머스 이력서 — 현행 화면 분석 보류

근거: [2019년 공식 이력서 클리닉 안내](https://programmers.co.kr/pages/resume-clinic-1906). **과거 안내 본문 관찰.**
- 첫 화면·숫자: 안내는 행사명과 참가 규모를 먼저 제시한다. 이는 이력서 화면이나 개인 성과 표현의 근거가 아니다.
- 카드·리스트·여백·글자·다크: 현행 편집·열람 화면을 확보하지 못했다. 안내의 등록 링크도 열리지 않아 해당 UI 속성은 분석에서 제외한다.
- 문체·성취/경력: 안내는 존댓말로 기술·근무 경험·프로젝트 경험의 특징을 검토한다고 설명한다. 차용 범위는 기술을 경험과 함께 설명한다는 내용 원칙에 한정한다.

### 10. 점핏 이력서 — 관리 행동을 분명하게 표시

근거: [공식 이력서 가져오기 안내](https://team.jumpit.co.kr/fff2defd-6806-810b-b2eb-e97dbd6fddb2), [첨부 화면](https://cdn.lazyrockets.com/notion-image/v1/7ef358ffd8c296de865d015588d31683d6dc6c9fee9a1762b545afc970019c85.png). **본문·이미지 관찰.**

## 포트폴리오에 바로 쓸 패턴 12개

아래는 관찰을 번역한 **설계 제안**이다. 성능·채용 효과는 검증하지 않았으며, 효과에 관한 판단은 [추정]이다. 데스크톱은 1280px, 모바일은 390px 폭을 검토 기준으로 삼는다.

1. **첫 화면에서 한 프로젝트를 이해시키기** — 이름 24px → 해결한 문제·결과 제목 32px → 맥락 16px 두 줄 → 대표 시연 순서. 상단 인사말이나 역할 표어로 한 화면을 쓰지 않는다. 토스 원칙·당근 질문 구조에서 차용.
2. **대표 결과 한 개를 크게** — 프로젝트명 24px 아래 핵심 결과 32px, 단위·비교 대상 16px, 측정 조건 14px. 숫자가 없으면 검증된 산출물 이름을 24px로 쓴다. 토스·뱅크샐러드의 요약 방식에서 차용.
3. **프로젝트별 묶음 안에 시간순 기록** — 실제 로고가 있으면 40×40px, 없으면 프로젝트명만 표시. 기간 14px → 결과 → 시연 → 기술 판단 → 수상·발표 목록 순서. 프로젝트는 최근순, 내부 이력도 날짜 기준 최근순으로 통일한다. 원티드 구조를 응용.
4. **카드는 프로젝트에만, 이력은 행으로** — 프로젝트 컨테이너 안쪽 여백 24px, 모바일 20px. 수상·발표는 행 사이 12px, 날짜 14px·제목 16px로 반복한다. 목록의 항목마다 카드를 겹치지 않는다. 토스 목록·네이버 속성 반복을 응용.
5. **결과와 근거를 같은 자리에서** — 개선 전·후를 같은 단위의 두 막대 또는 두 화면으로 나란히 배치하고 16px 간격을 둔다. 바로 아래 14px로 데이터 범위·실행 조건·근거 링크를 표시한다. 배민 비교 방식 차용; 비교 가능한 데이터가 없으면 막대는 만들지 않는다.
6. **시연은 요약 바로 아래** — 대표 프로젝트에 16:9 영상 영역을 펼쳐 두고, 모바일에서는 결과 다음에 배치한다. 재생 전 포스터에도 핵심 기능이 보여야 한다. 토스의 가치 우선 원칙을 응용하며 영상·포스터는 실제 제공 자산만 쓴다.

8. **요약을 남기는 상세 펼치기** — 문제·역할·결과·대표 화면은 항상 노출하고, 실험 조건·대안 비교만 아래에 접는다. 열기 영역은 최소 높이 44px, 16px 문구로 무엇이 나오는지 적는다. 리멤버의 요약/상세 분리와 토스 원칙을 응용.
9. **다크에서도 면의 높이를 구분** — 페이지 `#121416`, 프로젝트 면 `#1B1F23`, 주 텍스트 `#ECEFF3`, 보조 `#B5BDC7`을 출발값으로 제안한다. 강조색은 결과·선택 상태에만 사용하고 대비는 구현 후 검증한다. 당근의 배경/전경 역할 분리와 토스 비교 화면을 응용.
10. **네 단계 글자와 일정한 간격** — 32/24/16/14px, 본문 행간 1.6, 구획 간격 48px, 문단 간격 16px. 제목 `balance`, 본문 `pretty`, 한국어 `keep-all`, 숫자 `tabular-nums`를 적용한다. 당근의 스타일 축소 원칙을 소규모 사이트에 맞게 제안.
11. **문체도 정보 역할에 맞추기** — 제목은 문제·결과가 드러나는 짧은 문장, 경력은 개조식, 조작 안내만 짧은 해요체. 결과 설명은 16px 두 줄 안에서 `한 일 → 확인된 변화`를 연결한다. 원티드 샘플과 토스·당근의 화면/설명 문체 구분을 응용.
12. **세 프로젝트를 같은 틀로 비교** — 이름 24px, 기간·역할 14px, 결과 24px, 시연·근거 링크 16px의 순서와 좌측 시작선을 맞춘다. 발표자료는 항목 아래 웹 미리보기를 제공한다. 네이버의 고정 속성과 원티드의 목록/상세 병치를 응용; 모바일은 한 열로 배치한다.
